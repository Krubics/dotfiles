GTK 3 → GTK 4

The object model survived. The machinery underneath changed: GTK 4 turns widget output into a reusable scene graph, routes input through controllers, and makes composition explicit.

Not “GTK 3, but faster.”A source- and ABI-breaking redesign around modern rendering and display systems.
00 / ORIENT

Same language.
Different grammar.

If you know GTK 3, the concepts remain recognizable. The places where those concepts connect are what moved.

Still foundational

  • Widgets arranged in a parent–child tree
  • GObject properties, references, and signals
  • GLib’s main loop and main-thread UI work
  • CSS-driven visual styling
  • GDK as the platform and window-system boundary
  • Pango for internationalized text

Rewired in GTK 4

  • Drawing becomes snapshot → scene graph → renderer
  • Input signals become controllers and gestures
  • Generic containers become widget-specific child APIs
  • Layout policy becomes an explicit manager
  • Lists become model + selection + item factory
  • Blocking and X11-centric APIs largely disappear

02 / COMPARE

The shifts, aligned.

Like-for-like comparisons. Read across each row rather than treating GTK 4 as a list of removals.

Concern
GTK 3
GTK 4

Rendering

A widget handles draw() and emits Cairo commands into a context.

A widget handles snapshot() and appends GSK render nodes. OpenGL, Vulkan, or Cairo renders the resulting graph.

Input

Connect to low-level widget signals such as button-press-event or scroll-event.

Attach GtkGestureClick, GtkEventControllerKey, scroll, motion, focus, drag, or drop controllers.

Children

gtk_container_add() and gtk_box_pack_start() expose generic container behavior.

gtk_window_set_child() and gtk_box_append() make ownership and structure specific to each widget.

Layout

Container classes commonly own their measurement and allocation logic.

GtkLayoutManager separates layout policy from the widget. Expansion and alignment live on children.

Large lists

GtkTreeView, tree models, and cell renderers.

GListModel + selection model + GtkListView/GtkColumnView + item factory. Better fit for virtualization.

Lifecycle

gtk_widget_destroy() and widget-specific destruction patterns are common.

Widgets follow normal GObject ownership more closely. Parents hold children; cleanup belongs in dispose/finalize.

Application

gtk_init(), gtk_widget_show_all(), and gtk_main() are common.

GtkApplication, g_application_run(), and gtk_window_present(). The gtk_main_*() family is gone.

Platform

More APIs expose X11-era concepts: GdkScreen, visuals, root windows, and child GdkWindows.

GdkDisplay and GdkSurface fit Wayland and other backends. Child widgets normally share their toplevel surface.

04 / PORT

Where migration effort hides.

A mostly stock-widget application may port cleanly. These seams—not line count—usually determine the real cost.

High rewrite

Custom drawing

Replace draw() assumptions with snapshots and GSK nodes. Cairo remains available inside a node when necessary.

Target → snapshot()
High rewrite

Tree views

Reframe trees, sorting, selection, and cells around list models and factories. There is no mechanical one-call swap.

Target → model + factory + view
High rewrite

Deep subclasses

Several concrete widgets can no longer be subclassed. Prefer a custom GtkWidget that composes child widgets.

Target → composition
Medium rewrite

Event signals

Replace direct event signals with purpose-built controllers and gestures; adjust callbacks to their higher-level semantics.

Target → controllers
Medium rewrite

Dialogs and clipboard

Code that depends on nested blocking loops must become signal- or callback-driven and tolerate asynchronous results.

Target → async flow
Usually mechanical

Basic containers

Replace generic add/remove and packing calls with widget-specific APIs, then move expand/fill behavior onto children.

Target → explicit child APIs

The practical answer

Use GTK 4 for new work. Treat an existing app as a port, not an upgrade.

GTK 4 rewards applications that model UI as composition and state. The hardest GTK 3 code to move is usually the code most coupled to immediate drawing, concrete widget internals, blocking control flow, or X11 concepts.

Rule of thumb: stock widgets + modern GtkApplication → easier; custom renderers + GtkTreeView + nested dialogs → deliberate rewrite.

What GTK 4 does not change

GTK is still a stateful, retained widget toolkit. It is not a web DOM, immediate-mode GUI library, or thread-safe UI runtime.

What “GPU accelerated” means

Widgets describe reusable render nodes; GSK chooses a renderer. It does not mean application code should issue raw GPU commands.
