GTK theming fieldwork Lesson 0001 · about 8 minutes

One skill · evidence before edits

Diagnose a GTK theme failure with three gates.

When a rule “does nothing,” do not rewrite it yet. First find the earliest gate it failed: the stylesheet loaded, the selector matched, or the declaration applied.

Tangible win: classify a GTK theming failure in under one minute.

01 / Model

CSS travels through three gates.

GTK does not style a web DOM. Each widget exposes a tree of CSS nodes with node names, IDs, classes, and states. A rule affects a node only after all three gates pass. The GTK 4 CSS overview defines this model; each widget’s API page documents its own node tree.

Loaded

Did this application receive this stylesheet from a provider or known config path?

Test: provider list Pass → continue · Fail → stop

Matched

Does the selector describe a CSS node that actually exists in this widget tree?

Test: node tree Pass → continue · Fail → stop

Applied

Does this GTK version support the declaration, and did cascade or specificity win?

Test: computed style Pass → done · Fail → inspect value
Diagnostic rule: stop at the earliest failed gate. A perfect selector cannot repair an unloaded file; a supported property cannot repair a selector that matched nothing.
02 / Loaded

GTK 3 and GTK 4 load different files.

The major versions are parallel installations, not one shared theming target. Their per-user CSS paths are deliberately separate:

GTK 3 $XDG_CONFIG_HOME/gtk-3.0/gtk.css

Usually ~/.config/gtk-3.0/gtk.css.

GTK 4 $XDG_CONFIG_HOME/gtk-4.0/gtk.css

Usually ~/.config/gtk-4.0/gtk.css.

Waybar is a third case: it explicitly loads $XDG_CONFIG_HOME/waybar/style.css. Those application selectors—such as window#waybar and #workspaces—belong to Waybar’s own widget tree, not to every GTK application. See the project’s official styling guide.

On this workstation, Waybar 0.14.0 links to libgtk-3.so.0 and libgtkmm-3.0.so.1. Therefore, editing gtk-4.0/gtk.css is not a test of the installed Waybar. Re-check after upgrades:

ldd "$(command -v waybar)" | grep -E 'gtk|gtkmm'
# libgtk-3.so.0  → GTK 3 process
# libgtk-4.so.1  → GTK 4 process
03 / Matched

Selectors describe GTK’s node tree.

Read a selector from right to left. Your current Waybar rule #workspaces:not(.taskbar) button.active asks for an active button beneath a node whose ID is workspaces and whose classes do not include taskbar.

A GTK 4 widget may expose different node names or nesting than its GTK 3 counterpart. Copying a valid GTK 3 selector can therefore pass syntax parsing but match zero GTK 4 nodes. Use GTK Inspector instead of guessing.

04 / Applied

GTK CSS is not browser CSS.

Even after a selector matches, GTK must support the declaration and the rule must win the cascade. GTK 4 removed widget style properties and GTK-specific forms including -gtk-gradient, -gtk-icon-effect, and -gtk-icon-theme. The official migration guide is the source of truth for removed features.

Use Inspector’s CSS and computed-style panes: an unknown declaration, a crossed-out rule, or a different winning origin tells you this is the third gate—not a path or selector problem.

One extra layer: libadwaita is a styling library used by some GTK 4 apps. It is not another name for GTK 4. An app can be GTK 4 without libadwaita, and libadwaita can intentionally constrain application-level styling.
05 / Retrieve

Name the failed gate.

06 / Fieldwork

Use the model on one real rule.

Keep beside Inspector

Open the printable GTK theme diagnosis sheet and work down its three gates.

Ask your teacher

Send the agent one failed selector, the application name, and what Inspector shows. Ask follow-up questions about any unclear gate.

Primary reading: read the short GTK 4 CSS Overview, then locate the “CSS nodes” section on the API page for one widget you care about. Stop there; the purpose is to verify the mental model, not memorize the property catalog.
